# CPU 检索性能与扩容

0.6.2–0.6.6 实测记录，2026-09-10。各版本分别绑定冻结源码、数据库和独立进程测量。默认离线包仍使用 BM25；安装真实模型并执行 `semantic activate` 后，默认启用 `hybrid`。`hybrid_rerank` 必须显式选择。这里的耗时不包含宿主 AI 写分析的时间，不能视为整个算卦对话的耗时。

## 为什么先修检索路径

原路径每次查询解码全库案例、构造搜索文本，然后在 Python 中筛选。SQL 版本将可搜索状态、事项、目录、去重组和结构特征在入库时保存为小字段，先在 SQLite 中筛选，只读取候选或最终结果的完整原文。词法、向量和结构召回分别保留自己的入口，不能先用词法候选限制向量召回。

在同一份 4,081 块、1,830 案例的候选库上，14 个开发问题的 28 次规则/案例查询，重构前后 ID、排序、分数、引文、字段与分页标记完全一致。案例 BM25 平均 606.44 → 11.89 ms；规则平均 86.69 → 35.86 ms，包含首次分词初始化。真实 BGE 向量的 SQL 范围筛选与原 ID 集合筛选也通过 28 次完整结果等价检查。

每路候选预算是 `max(60, limit * 5)`，不随数据库总量或排除 ID 数增加。返回 3 项的规模实验每次只解码 3 个完整 payload；显式重排时才读取需要打分的候选文本。初次扩容优化的数据库格式为 `focused-2`，0.6.5 增加分层用神接口后为 `focused-3`；旧库需要随发布包更新或重新入库。

## 实测规模

以下为当前真实语料元数据和真实 BGE 向量的重复扩容实验，每项 7 次、模型编码不参与计时。复制条目共享去重组，原始完整正文未扩增，因此这些数据只衡量索引扫描、筛选和候选边界，不能衡量更多真实资料的召回质量。

| 元数据条目 | 案例 BM25 P50 | 规则 BM25 P50 | 结构召回 P50 | 案例向量扫描 P50 | 规则向量扫描 P50 |
|---:|---:|---:|---:|---:|---:|
| 5,911 | 9.51 ms | 14.93 ms | 30.82 ms | 11.29 ms | 19.66 ms |
| 10,000 | 10.69 ms | 23.50 ms | 53.72 ms | 19.08 ms | 33.67 ms |
| 50,000 | 23.10 ms | 153.31 ms | 210.91 ms | 126.87 ms | 277.51 ms |

50,000 条实验有 50,030 个向量窗口，规则向量扫描 P95 为 291.69 ms。查询进程峰值 RSS 为 108.62 MiB，包含分词器，不包含独立的模型进程。原库及实验库查询前后 SHA-256 均保持一致。

在真实 14 个开发问题上，新混合检索平均规则 147.18 ms、案例 158.40 ms；P95 分别为 521.20/175.32 ms。模型进程已预热，查询缓存状态混合，不能把这组数据宣传成新问题无缓存或冷启动的服务承诺。事项标签相符率不是相关性准确率。

另在全新独立工作进程上测了 50 个不同的自然中文问题（规则与案例各 25 个，`limit=3`）。仅以无关文本预热，全部实际查询首次未命中缓存，保留最慢样本。最终冻结版分别测得：

| 版本 | 检索 P50 | 检索 P95 | 最大值 | 冷启动加预热 |
|---|---:|---:|---:|---:|
| 0.6.2 | 98.98 ms | 124.85 ms | 428.61 ms | 9.21 s |
| 0.6.4 | 99.59 ms | 126.99 ms | 452.12 ms | 8.53 s |
| 0.6.6 | 100.90 ms | 125.98 ms | 462.26 ms | 8.45 s |

0.6.4 查询编码 P50/P95 为 62.38/68.47 ms，向量 SQL 扫描为 5.85/19.25 ms。全部有真实向量命中且未加载重排器，记录了全机争用。计时包括搜索函数和查询编码 HTTP，不含外层 MCP 进程启动、模型下载或 Astra 分析。原始查询、日志、代码和数据库哈希分别在 `.local/hybrid-fresh50-final062/` 、`.local/hybrid-fresh50-final064/` 与 `.local/hybrid-fresh50-final066/`。这些是固定本机负载结果，不能承诺任意规模、并发和新语料均保持该延迟。

## 为什么不默认重排

同一真实 `BAAI/bge-reranker-v2-m3`，CPU、8 个 Torch 线程，4 个独立编写的查询，各自固定 BM25 前 40 个完整文本，每种候选数重复 3 次。每次清除重排结果缓存，长文覆盖全部窗口。

40 候选 FP32 中位数约 12.9 秒，逐通道动态 int8 约 5.3 秒。int8 的前 4 项与 FP32 并不完全一致；它是可选的速度与排序取舍，不是无损优化。直接只重排前 4/8/12 个候选，相对 FP32 40 候选的前 4 项覆盖也明显下降。该比较衡量模型排序一致性，不证明模型本身的相关性正确。

第一组测量记录了推理进程和共享工作进程 CPU，但没有完整全机争用数据。另一次全机争用补测观察到共享编码占用约 5–6 核，此时 int8 40 候选可达到约 11.45 秒；两组结果应分开查看。因此不以小候选、缓存命中或空闲机器的最快一次承诺生产延迟。

启用方式：

```bash
python -m liuyao_mcp.semantic activate
# 需要完整重排时显式选择：
python -m liuyao_mcp.semantic activate --mode hybrid_rerank
```

单次工具调用也可传 `retrieval_mode="hybrid_rerank"`，不必改变默认配置。可选环境变量 `LIUYAO_RERANK_PRECISION=dynamic_int8_per_channel` 只量化重排器；默认 `float32`，embedding 仍为 FP32，向量缓存键不变。切换精度需要让自己的旧推理进程退出再启动，不能复用另一精度的工作进程或打分缓存。已有用户配置不会被发布包静默改写。

## 更多资料如何加入

正文切块、校订和向量编码在建库阶段完成。新版本复用未改变文本的编码缓存；用户查询时只编码当前问题。候选索引可用 `vector_index --no-activate` 生成，校验来源、引文、覆盖和版本后再发布或启用，不在查询过程中临时给整本书编码。

当前使用 SQLite 普通 BLOB 表与 `vec_distance_cosine` 精确扫描。它仍随符合筛选条件的向量数量增长，不是 ANN。sqlite-vec 官方也区分普通表距离扫描和 `vec0` 查询；仅安装扩展不能消除神经重排耗时。[sqlite-vec 查询文档](https://alexgarcia.xyz/sqlite-vec/features/knn.html)

扩容时固定查询组、来源版本、模型、候选数及输出预算，分别量 BM25、结构筛选、问题编码、向量扫描、重排和整体 P50/P95；另测模型冷启动和并发排队。每次新增资料都重新核对相关性，复制规模实验不能代替这一步。

如果实际资料增长后，向量扫描 P95 持续超过设定预算（例如 500 ms），再对同一查询组比较分区、`vec0` 或近似索引，同时量化漏召回；当前 50,000 条扫描实验不需要先迁移到独立向量服务。2 秒可作为常规预热查询的验收目标，尚未作为冷启动、并发或任意长查询的承诺。

复现索引规模测试：

```bash
python scripts/benchmark_retrieval_scaling.py --help
python scripts/audit_knowledge_index.py --database data/knowledge.sqlite
```
