# 发布与版本管理

发布源为GitHub仓库与GitHub Releases。插件目录名称为`liuyao`，插件名称为`liuyao-assistant`。当前版本为0.4.2。

## 版本对应

- Python版本定义在`src/liuyao_mcp/__init__.py`。
- 插件清单使用相同版本，`.mcp.json`固定指向该版本Release包。
- 程序和预建数据库随同一发行包分发，用户更新时不重新建库。
- 开发版缓存后缀只用于本机迭代，不带入正式发行版。

## 发布步骤

1. 修改代码、资料或指引，同步版本、插件清单和Release地址，更新CHANGELOG。
2. 运行测试，校验插件与Skill；在独立目录重建数据库，避免运行中的旧服务占用开发库。
3. 构建并验证发行包：

```powershell
.\.venv\Scripts\python.exe scripts/build_release.py
.\.venv\Scripts\python.exe scripts/smoke_release.py .\.venv\Scripts\uvx.exe --python 3.11 --from "$PWD/dist/liuyao_mcp-0.4.2-py3-none-any.whl" liuyao-mcp
.\.venv\Scripts\python.exe scripts/smoke_release.py .\.venv\Scripts\uvx.exe --offline --python 3.11 --from "$PWD/dist/liuyao_mcp-0.4.2-py3-none-any.whl" liuyao-mcp
```

4. 提交代码，**只推对应版本标签，先不推main**，例如`git tag v0.4.2`、`git push origin v0.4.2`。标签触发Release工作流，在Linux重新建库、测试、打包并上传发行物。
5. 工作流从实际Release URL执行插件启动命令，使用独立uv缓存验证首次下载，再以同一命令阻断HTTP/HTTPS代理复测。确认工作流全部成功，必要时完成Windows首次下载验证。
6. 最后`git push origin main`，让用户订阅的插件目录指向已经可下载、已验证的版本。若远端main有新提交，先保留并合并其改动，不强推。不要提前把指向新Release的插件配置推送main。

正式产物包括：服务sdist、wheel、固定下载名`liuyao-mcp.tar.gz`、插件ZIP、`install.ps1`和`SHA256SUMS`。插件ZIP包含目录清单、Skill、MCP配置与安装入口；程序和数据库由配置指定的Release包提供。安装器不要求开发者目录或本机绝对路径。

发布过的版本标签和资产不覆盖；修复后提升补丁版本，新能力提升次版本。工作区构建成功不能当作GitHub发布成功，需核对工作流状态和实际Release资产。

## 更新与回退

Git插件目录复用Codex原生自动更新：本机CLI 0.153.0对应源码包含启动时升级Git目录并刷新已安装插件缓存的逻辑，不需要另写插件更新器。不能由此承诺推送后立即生效或客户端持续开启时定时轮询。[原生更新实现](https://github.com/openai/codex/blob/rust-v0.153.0/codex-rs/core-plugins/src/manager.rs#L2735-L2939)

0.4.2使用版本化wheel URL，uvx首次自动下载新版程序及数据库，后续复用缓存。插件入口不带`--offline`，安装脚本的离线自检仍显式带该选项。日常升级不需要运行脚本，安装脚本保留为首次安装与修复入口。先发布并验证Release，再推进main，避免用户先拿到指向缺失资产的配置。

已缓存且配置仍指向该版本时可离线使用；配置已指向未缓存版本时没有自动回退。原生目录升级可能先刷新插件缓存，不能将脚本后续准备失败描述为必然保留旧插件。

需要固定旧版本时，从对应tag安装插件目录并准备其配置指定的服务包；直接MCP用户可以固定Release URL。不要在未下载依赖时直接要求`--offline`启动新版本。

模型权重、实验向量索引、本机路径配置与测试日志不进入默认发行包。SQLite向量和神经模型实验的状态见[实施验收](实施验收.md)。
